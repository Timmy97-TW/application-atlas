### 1. A new insights section: sequencing traps (insights.html#sequencing)

The timeline page already lists every dated fact for the cycle. What it does
not say out loud is that for an applicant carrying a portfolio or a research
supplement, the application deadline is frequently not the binding date. The
new section re-sorts dates already on the site by which one arrives first, in
three groups, twelve items, 22 citation markers, every source `official`:

- A portfolio's deadline is not the application's deadline. Stanford moves the
  Common App itself forward for arts-portfolio applicants (15 Oct for a 1 Nov
  REA round; 5 Dec for a 5 Jan RD round) — the only school of the 30 that does.
  Brown's SlideRoom portfolios (4 Nov) and Princeton's arts and Cornell's music
  supplements (6 Nov) fall *after* the 1 Nov application date. MIT's portfolios
  share the application date. Three different patterns in one cycle.
- Research material travels a different channel at each school: inside
  SlideRoom with a mentor letter (MIT), through the school's own portal only
  after submission (Johns Hopkins, Swarthmore), inside the Common App's
  Additional Information with the full paper explicitly unwanted (Harvey Mudd),
  or not at all (Duke).
- Test dates and system windows are hard edges: MIT EA and Caltech REA require
  the test to have been *taken* by 30 Nov; UC's filing window is 1 Oct–30 Nov
  with no ED or EA; Swarthmore's portal does not open until mid-October.

One item is tagged `[推論]`: that the date to plan against is the earliest of
the application, the portfolio upload, and a mentor's letter the applicant does
not control. The rest are `[事實]`.

## A deploy bug: data changes could reach readers from their cache

Found by accident, while checking the new front-page card: the card was in the
file the server sent, and absent from the page the browser rendered.

The HTML shells load every data file with a `?v=` cache-busting stamp, and the
stamp is a timestamp generated by `scripts/make-pages.js`. But that script is
only run when a page or data file is *added*, and it is not in CLAUDE.md's
end-of-run checklist. So every run that changed `site/data/*.js` without adding
a file shipped the new data under the old stamp, and a returning reader's
browser was entitled to serve the cached copy while the new file sat unread on
the server. Tonight's earlier merges are all in that category.

Fixed three ways:

- `scripts/make-pages.js` re-run, so all 17 shells now carry a fresh stamp
  (`mw5gqjdk`) and this deploy's data actually reaches returning readers.
- CLAUDE.md's "before finishing any run" list now requires running it whenever
  anything under `site/data/` or `site/assets/` changed, and warns that
  verifying a data change needs a cache-busting query rather than a plain
  reload — the same trap caught this check.
- The favicon link moved into the shell template rather than being edited into
  17 files, because regenerating the shells would have silently deleted it.
  That is the same class of mistake: hand-editing generated files.
